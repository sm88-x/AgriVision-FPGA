# live_stream 摄像头能力实测（B 组）

> 测于 2026-10-11 凌晨，被测设备：**电脑内置的 HP 5MP Camera**

> 脚本：`src/software/app/camera_capture.py --probe`，原始数据同目录 `camera_capability.json`

## 1. 结论（三句话）

1. **只有编号 0 能开，而且必须指定 DSHOW 后端**——不指定后端（或指定 MSMF）直接打不开。

2. **驱动只认三档分辨率**：640×480、640×360、1280×720。请求 320×240 / 256×256 / 800×600

   会被静默忽略并回落到别的档位，所以**板端要的 320×240、256×256 必须由我们在 PC 侧缩出来**。

3. **实测只有约 15 FPS**（帧间隔中位数 64 ms），不是 30 FPS。详见第 4 节的原因判断。

## 2. 设备枚举

| index | 后端 | 能打开 | 说明 |
|---|---|---|---|
| 0 | dshow | **是** | 原生 640×480，读到首帧 (480, 640, 3) |
| 0 | msmf | 否 | — |
| 0 | any | 是 | 能用，但实测不如显式 DSHOW 稳，脚本默认走 DSHOW |
| 1 | 全部 | 否 | 系统里那个 `HP IR Camera`（Windows Hello 红外），OpenCV 打不开 |
| 2 | 全部 | 否 | 不存在 |

`CAP_PROP_FPS` 在 DSHOW 下返回 **-1**（驱动不给这个属性），所以帧率只能实测，不能读。

## 3. 分辨率协商结果（每档实测 2 秒）

| 请求分辨率 | 实际协商到 | 实测帧数 | 实测 FPS | 帧间隔中位 | 帧间隔最大 |
|---|---|---|---|---|---|
| 640×480 | 640×480 | 31 | 15.05 | 64.3 ms | 81.5 ms |
| 320×240 | **640×360** | 30 | 15.00 | 64.8 ms | 81.2 ms |
| 256×256 | **640×360** | 31 | 15.17 | 64.0 ms | 84.1 ms |
| 1280×720 | 1280×720 | 32 | 15.66 | 64.7 ms | 80.9 ms |
| 800×600 | **640×480** | 31 | 15.02 | 64.1 ms | 82.7 ms |

加粗的四个是"请求被忽略、驱动回落到别的档位"。**这说明不能指望通过设置属性拿到目标尺寸。**

## 4. 为什么只有 15 FPS（判断 + 待复测）

三档分辨率的帧间隔都稳定在 64 ms 上下，且分辨率降到 320×240 也**没有变快**——

如果是带宽或算力瓶颈，降分辨率应该明显提速。所以更像是**采集端被曝光时间限制住了**：

这次是凌晨在暗光房间里测的，内置摄像头自动曝光把每帧曝光时间拉长，帧率就掉到 15。

**2026-10-11 白天复测（正常光照，同一台机器同一颗摄像头）**：

| 请求分辨率 | 实际协商到 | 实测 FPS | 帧间隔中位 | 帧间隔最大 |
|---|---|---|---|---|
| 640×480 | 640×480 | 24.28 | 33.1 ms | 114.6 ms |
| 320×240 | **640×360** | 29.02 | 32.0 ms | 63.8 ms |
| 256×256 | **640×360** | 29.29 | 32.1 ms | 65.6 ms |
| 1280×720 | 1280×720 | 29.27 | 32.2 ms | 64.6 ms |
| 800×600 | **640×480** | 29.53 | 32.2 ms | 48.7 ms |

复现命令：`python src/software/app/camera_capture.py --probe`

**结论**：凌晨测到的 15 FPS 是**暗光下自动曝光把曝光时间拉长**造成的，**不是这颗摄像头的

固有限制**。白天正常光照下 640×480 约 **24 FPS**、其余档位约 **29 FPS**。

因此验收口径按"640×480 ≥ 24 FPS"记：300 帧压力测试在 24 FPS 下约需 **12.5 秒**

（原先按 15 FPS 估的 20 秒作废）。分辨率协商问题与凌晨一致，仍由 PC 侧 letterbox 兜住。

## 5. 对 live_stream 设计的直接影响

1. **采集口径固定为 640×480**：原生支持、最接近板端主档，缩放比例也最舒服。

2. **320×240 / 256×256 由软件缩放产出**，且沿用 pipeline_validation 已验证的 letterbox 口径

   （白底、保持比例、缩小用 `cv2.INTER_AREA`），避免"相机直出"和"Golden 输入"两张不同的图。

3. **灰度转换不用 `cv2.cvtColor`**，用 `run_pipeline.rgb2gray` 的

   `(77R+150G+29B+128)>>8`——cv2 的 BT.601 舍入不同，逐像素 Golden 比对会差 ±1。

4. **必须有丢帧统计**：15 FPS + 偶发 80 ms 间隔（已经超过中位数的 1.25 倍），

   说明"零丢帧"不能靠嘴说；脚本按帧间隔推断丢帧数并把每次跳变记进日志。

## 6. 复现方式

```

python src/software/app/camera_capture.py --probe --json docs/evidence/live_stream/camera_capability.json

python src/software/app/camera_capture.py --save 10 --out report/live_stream/golden_sample10

```

依赖：`numpy`、`opencv-python`。

补一句实测结论：本次测量用的是 **`opencv-python-headless`（5.0.0）**，

采集本身完全正常——headless 只是不带 `imshow` 这类 GUI 窗口，`VideoCapture` 不受影响。

只有当我们自己要弹预览窗口时，才需要换成普通版 `opencv-python`。
